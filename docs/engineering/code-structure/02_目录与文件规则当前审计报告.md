## 6. 推荐收敛顺序

| 优先级 | 范围 | 原因 | 验收 |
|---|---|---|---|
| P1-1 | Swift 生产代码 >400 行 | 直接违反硬阈值，影响日常维护。 | Swift P1 扫描中生产代码为 0。 |
| P1-2 | Rust 生产代码 >500 行 | 直接违反硬阈值，且集中在 AI runtime / HTTP / provider 边界。 | Rust P1 扫描中生产代码为 0 或仅剩正式豁免。 |
| P1-3 | Swift / Rust 超长测试 | 测试维护成本高，容易阻塞后续重构。 | 超长测试拆分或补完整豁免。 |
| P1-4 | Rust 根 `src` 业务模块 | 违反根产品 crate 职责边界。 | `maohuoban-rust/src` 仅保留入口、装配、诊断入口和必要聚合。 |
| P2 | 251-400 行 Swift、301-500 行 Rust、多类型聚合 | 规模较大，应随 Feature 迭代逐步清理。 | 新增代码不扩大 P2；触碰文件时顺手拆分。 |
| P3 | 测试目录镜像整理、UI Test 目录化、Widget 子目录化 | 对行为风险低，适合独立结构任务。 | 目录扫描输出持续下降。 |

## 9. 不变约束

| 约束 | 说明 |
|---|---|
| 只做结构迁移 | 不改变业务逻辑、API 语义、UI 行为、导航行为和测试断言语义。 |
| 保护用户改动 | 当前工作区已有未提交文件，后续拆分应在独立 worktree 中执行。 |
| 访问控制最小化 | 拆分 helper 时优先保持 `private` / internal，避免扩大公开 API。 |
| SwiftUI 渲染纯净 | 拆分不得引入 `body` 或同步 helper 中的持久化、全局状态写入、通知发送等副作用。 |
| Rust 模块导出稳定 | 拆分前先设计 `mod` 导出，保持对外 crate API 稳定。 |
| 测试保持有效 | 拆分测试文件时保留原断言强度，不降级为存在性检查。 |
| 临时日志纪律 | 本目标不需要临时日志；如后续拆分引入诊断日志，验证后必须清理。 |

## 10. 风险

| 风险 | 处理 |
|---|---|
| 超长测试拆分导致 fixture 重复 | 先抽 test support，再迁移 case，避免复制大型桩。 |
| SwiftUI 页面拆分导致状态传递膨胀 | 子 View 只接收实际读取数据，动作通过显式闭包转发。 |
| Rust runtime 拆分破坏内部状态机 | 先补等价测试或运行现有 runtime contract，再做纯结构迁移。 |
| provider / HTTP 拆分引入错误映射回归 | 先固定错误分类、脱敏日志、SSE 事件序列测试。 |
| 旧豁免长期失效 | 每个超长文件必须在拆分或正式豁免之间二选一，豁免需写明责任和重新评估条件。 |
| 本地生成文件干扰审计 | 最终门禁以 `git ls-files` 为准，工作区卫生问题单独处理。 |
