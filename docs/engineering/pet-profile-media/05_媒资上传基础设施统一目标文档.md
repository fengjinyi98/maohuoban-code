# 媒资上传基础设施统一目标文档

- 更新时间：2026-06-24
- Goal：统一用户资料、宠物档案、UGC、商品/服务、医疗记录和视频等媒资上传基础设施，建立清晰的上传策略、大小限制、进度回调、派生图生成、错误语义和 SDK 观测标准；同时补齐用户资料编辑页“内容无变更不提交”的保存守卫。
- 执行方式：先用目标文档固化依据和边界，再按 TDD 小步落地；后端先补齐 profile 上传契约和错误语义，iOS 再沉淀统一 encoder / uploader，最后迁移用户和宠物链路。

---

## 1. 当前结论

| 项 | 结论 |
|---|---|
| 上传链路归属 | 媒资上传属于跨业务基础设施，用户头像、用户背景、宠物头像、宠物背景、商品图片、UGC 图片和视频应共享同一套上传策略、进度回调和观测字段 |
| 当前失败根因方向 | 用户头像裁剪后编码为 19MB PNG，multipart body 已生成并发出；后端 profile multipart 解析或 body limit 处理失败后统一映射为 `profile.media_file_required`，前端展示“请先选择图片” |
| Toast 来源 | “请先选择图片”来自后端业务错误 message，经前端错误展示链路透传 |
| 宠物链路可复用点 | 宠物头像和背景已使用 JPEG 编码，并走 multipart 上传；该链路已具备用户资料侧应复用的方向 |
| profile 链路缺口 | profile 路由已接收 multipart，但缺少与宠物路由同级的 `DefaultBodyLimit` 配置，multipart 读取错误也缺少细分错误码 |
| 图片格式策略 | 照片类源图默认使用 JPEG / HEIC / WebP 等有损照片格式；透明图、截图、线稿和需要 alpha 的素材保留 PNG |
| 清晰度策略 | 720p 只能作为派生图规格，不能作为源图上传的通用上限；2K、4K 级图片应按业务场景允许上传并由后端生成多档派生资源 |
| 压缩职责 | iOS 负责方向修正、合理编码、控制首跳体积和上传体验；后端负责硬限制、真实 MIME / 解码校验、源图存储、派生图生成和安全兜底 |
| 进度回调 | 所有媒资上传入口都需要进度回调，后续 URL、图片、视频和文件上传统一暴露 progress |
| 无变更保存 | 用户资料编辑页需要参考宠物编辑档案页，内容未变更时直接结束保存流程，避免向后端发请求和误触发 Toast |

## 2. 目标边界

## 2.1 本目标期必须完成

| 范围 | 目标 |
|---|---|
| 统一上传策略 | 建立 `MediaUploadPolicy`，按 avatar、cover、ugc image、commodity image、medical image、video 等用途定义 body limit、文件 limit、像素 limit、格式和派生规格 |
| profile body limit | 为用户头像和背景上传路由配置明确 `DefaultBodyLimit`，与应用层文件限制形成一致契约 |
| profile 错误语义 | 区分缺少文件、body 过大、multipart 无效、文件过大、MIME 不支持、图片解码失败等错误 |
| iOS 编码器 | 新增统一 `MHBMediaUploadEncoder` 或同级基础设施，用户和宠物链路使用相同编码策略 |
| iOS 上传器 | 用户和宠物媒资统一走 multipart + `uploadTask` + progress，不保留无进度上传分支 |
| 用户资料无变更守卫 | 个人资料编辑页保存前做 dirty 判断，字段和媒体均未变更时不发 `PATCH /profile/me`，不展示成功 Toast |
| SDK 观测 | 上传前、multipart 生成、uploadTask 启动、进度、后端 parse、应用校验、对象存储、派生图生成都输出稳定观测字段 |
| 文档与测试 | 更新接口契约、补充 Rust / iOS 定向测试，覆盖大小限制、错误码、进度回调和无变更保存 |

## 2.2 本目标期暂不做

| 暂不做 | 原因 |
|---|---|
| 完整 CDN 图片服务 | 当前先建立上传和派生策略，CDN header 与缓存策略后续纳入远程图片治理 |
| 视频分片全量实现 | 本目标期先定义视频策略和接口方向，较大视频后续走直传或分片 |
| 全业务一次性迁移 | 先迁移用户资料和宠物档案，UGC、商品、医疗记录按业务开发节奏接入 |
| 云端智能压缩 | 第一阶段使用确定性派生图规格和格式策略，智能压缩后续基于质量指标评估 |

## 4. 推荐媒资策略

## 4.1 类型与限制

| 媒资用途 | HTTP body limit | 单文件建议 limit | 源图建议 | 派生规格 | 默认格式 |
|---|---:|---:|---|---|---|
| 用户 / 宠物头像 | 16MB | 8MB | 最长边 2048，头像裁剪后保留高质量主图 | 256、512、1024 | JPEG 0.90；透明头像保 PNG |
| 用户 / 宠物背景图 | 32MB | 16MB | 最长边 3840，允许 2K / 4K 级上传 | 1080、1600、2560 | JPEG 0.90 或 HEIC |
| UGC 图片 / 相册 | 32MB | 16MB | 保留 source 或高质量主图，像素上限按 64MP 评估 | 720、1080、1600、2560 | JPEG / HEIC / WebP |
| 商品 / 服务图片 | 32MB | 16MB | 建议 1500x1500 以上，最高 64MP | 800、1600、2560 | JPEG / WebP |
| 医疗 / 报告图片 | 32MB | 20MB | 保留可读源图，弱压缩 | 1080、1600、2560 | JPEG 高质量；截图可 PNG |
| Live Photo still | 32MB | 16MB | 与背景图策略一致 | 1080、1600、2560 | JPEG / HEIC |
| 短视频 | 512MB 起步 | 512MB 起步 | 按时长、码率和分辨率策略校验 | 封面、预览、转码档 | MP4 / MOV |

说明：

| 项 | 规则 |
|---|---|
| HTTP body limit | 需要略大于单文件 limit，容纳 multipart boundary、字段和 metadata |
| 单文件 limit | 应用层真实业务限制，错误码要可展示 |
| 源图 | 用于保留质量和后续派生，不能用 720p 作为通用源图标准 |
| 派生图 | 服务列表、卡片、详情、预览和弱网场景，由后端统一生成 |

## 4.2 格式策略

| 输入类型 | 推荐输出 | 原因 |
|---|---|---|
| 相机照片 / 宠物照片 / 背景照片 | JPEG 0.88-0.92 或 HEIC | 照片内容用 PNG 会产生过大体积，JPEG / HEIC 更适合移动上传 |
| 透明头像 / 贴纸 / 带 alpha 素材 | PNG | 需要保留透明通道 |
| 截图 / 文档扫描 / 医疗报告 | PNG 或高质量 JPEG | 文字可读性优先，根据实际体积和边缘质量选择 |
| 商品图 | JPEG / WebP | 兼顾清晰度、体积和 CDN 分发 |
| 视频 | MP4 / MOV | iOS 采集和服务端转码链路兼容性更高 |

PNG 失败的根因方向是“照片类内容被无损 PNG 编码后体积过大，并触发 profile 上传链路的 body limit / multipart parse / 应用层 limit 语义问题”。处理方式是建立格式策略和后端错误语义，而不是把问题归因到某个 PNG 解码器严格。

## 5. 推荐数据流

```text
Picker / Camera
  -> normalize orientation
  -> crop metadata / optional crop
  -> encode by MediaUploadPolicy
  -> multipart upload with progress
  -> backend body limit
  -> multipart parse
  -> application validation
  -> object store source
  -> generate derivatives
  -> persist media asset + binding
  -> response media asset + URLs
  -> SDK diagnostics timeline
```

| 步骤 | 职责 | 观测字段 |
|---|---|---|
| 选择 / 拍摄 | iOS 获取本地媒资 | picker kind、pixel width/height、source UTType |
| 裁剪 / 方向修正 | iOS 生成待上传图像 | crop rect、output pixels、scale |
| 编码 | iOS 按 policy 输出文件 | mime、fileName、byteSize、quality、policy id |
| multipart | iOS 生成请求体 | path、fileCount、bodyBytes、fieldKeys |
| 上传 | iOS `uploadTask` | progress sent/expected、trace id、duration |
| body limit | Rust HTTP | content length、limit、route |
| multipart parse | Rust HTTP | part name、fileName、mime、bytes、parse error |
| 应用校验 | Rust application | media kind、file limit、mime allowlist、pixel limit |
| 存储 / 派生 | Rust infrastructure | object key、derivative kind、width、height、bytes |
| 响应 | Rust / iOS | status、code、message、asset id、binding id |

## 6. 后端目标

| 任务 | 目标文件 | 要求 |
|---|---|---|
| 媒资策略模型 | `maohuoban-rust/crates/*-application` 或共享 media crate | 定义 `MediaUploadPolicy`，按用途提供 body limit、file limit、mime allowlist、pixel limit、derivative plan |
| profile body limit | `maohuoban-rust/crates/maohuoban-profile-http/src/profile/router.rs` | 头像、背景上传路由配置 `DefaultBodyLimit::max(...)`，值来自统一 policy |
| multipart 错误细分 | `maohuoban-rust/crates/maohuoban-profile-http/src/profile/router.rs` | `next_field`、`field.bytes`、`field.text`、缺 file、body too large 分别映射到稳定错误码 |
| 应用层文件限制 | `maohuoban-rust/crates/maohuoban-profile-application/src/profile/ports.rs` | 头像 / 背景 limit 与 policy 对齐，避免 HTTP 和 application 限制冲突 |
| MIME 与解码校验 | profile / pet application 或共享 media service | 根据真实内容校验 MIME、图片解码、像素数量和尺寸 |
| 派生图策略 | media infrastructure | 源图入对象存储后生成多档派生图，返回可用于头像、卡片、详情和背景的 URL |
| SDK 观测 | profile / pet HTTP、application、infrastructure | 统一记录 route、kind、mime、bytes、limit、parse status、asset id、duration |
| 契约测试 | `maohuoban-rust/tests` 或对应 crate tests | 覆盖成功上传、缺文件、body 超限、文件超限、错误 MIME、解码失败 |

建议错误码：

| 错误码 | HTTP | message 建议 | 场景 |
|---|---:|---|---|
| `profile.media_file_required` | 400 | 请先选择图片 | multipart 中没有 `file` part |
| `profile.media_body_too_large` | 413 | 图片太大，请选择较小的图片 | HTTP body 超过路由 limit |
| `profile.media_file_too_large` | 413 | 图片太大，请选择较小的图片 | 文件超过应用层单文件 limit |
| `profile.media_multipart_invalid` | 400 | 图片上传数据无效，请重试 | multipart 结构损坏或读取失败 |
| `profile.media_type_unsupported` | 415 | 暂不支持该图片格式 | MIME 或真实文件类型不在 allowlist |
| `profile.media_decode_failed` | 422 | 图片解析失败，请更换图片 | 图片解码失败或像素信息不可读 |

| 无变更保存守卫 | Profile edit Store / Screen | 对比初始表单、当前表单和媒体草稿；无变更时直接退出保存状态 |
| SDK 观测 | profile / pet upload path | 上传前记录 pixels、mime、bytes、quality、policy id、progress、toast source |
| 单元测试 | `maohuobanTests` | 覆盖 JPEG/PNG 策略、multipart 字段、progress 回调、无变更不发请求 |

用户资料无变更保存建议数据流：

```text
onAppear load profile snapshot
  -> edit fields mutate draft state
  -> save tapped
  -> compare snapshot vs draft
  -> if unchanged: end save flow without network and without success toast
  -> if changed: submit patch / media upload by changed parts
```

## 11. 不变约束

| 约束 | 说明 |
|---|---|
| 清晰度 | 不把 720p 作为源图通用上限；720p 只作为派生图规格 |
| 进度 | 所有媒资上传都暴露 progress callback |
| 上传协议 | 图片、视频和文件上传统一走 multipart / 后续直传协议，不回退 JSON base64 |
| 错误语义 | 后端真实错误必须以准确错误码返回，前端 Toast 只展示明确 message |
| SwiftUI 副作用 | 编码、上传、Toast 和 dirty 判断都在用户事件或 Store 命令入口触发 |
| 架构 | View 只转发事件；上传策略、编码、网络和状态转换进入 Infrastructure / Store / Repository |
| 临时日志 | ✅ 已清理 — 16 处调试打印在实现验证后移除 |
| 用户体验 | 保持现有裁剪、本地预览、背景展示和 Liquid Glass 体验 |

## 12. 风险

| 风险 | 处理 |
|---|---|
| 允许更大源图导致弱网上传慢 | iOS 显示进度、支持取消和重试；后端记录耗时和大小 |
| 后端生成多档派生增加任务耗时 | 上传响应可先返回源图和处理中状态，派生图异步完成后刷新 |
| HEIC / WebP 兼容性不一致 | 第一阶段 iOS 默认 JPEG，HEIC / WebP 按平台能力和服务端解码能力逐步启用 |
| profile 和 pet policy 迁移出现限制差异 | 先用测试锁定现有限制，再通过统一 policy 调整 |
| 错误码改动影响前端 Toast | 前端错误展示以后端 `message` 为准，测试覆盖核心错误码 |
| 大视频占用后端内存 | 视频路线规划直传或分片，当前仅定义基础限制和观测 |
