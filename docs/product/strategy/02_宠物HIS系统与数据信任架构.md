## 1. 核心结论

毛伙伴的宠物 HIS 不应被定义为宠物店收银系统，也不应被定义为多家医院互相透明共享完整病历的平台。

它应该被定义为：

> **医院内部可信医疗业务系统 + 宠物主授权的统一健康档案 + 转诊、保险和复诊协作的数据基础设施。**

系统设计必须同时满足三方诉求：

| 角色 | 核心诉求 | 系统承诺 |
|---|---|---|
| 医院 | 保护客户资产、治疗经验、经营数据 | 原始 HIS 数据归医院租户控制，跨院只共享授权数据包 |
| 宠物主 | 拥有连续、可携带、可复诊的宠物健康档案 | App 展示医院发布后的健康档案，不直接暴露医院内部记录 |
| 平台 | 建立医疗协作、保险理赔和长期宠物档案闭环 | 后端具备多租户隔离、授权、审计、导出和合规证明能力 |

最重要的产品边界是：

> **后端可以为系统运行处理医院数据，但平台人员、其他医院和宠物主不能默认查看医院原始 HIS 数据。**

## 2. 这份文档解决什么问题

这份文档回答五个关键问题：

1. 人类医院 HIS 系统通常是什么样的。
2. 人类医院之间是否共享病历和用药信息。
3. 宠物 HIS 应该借鉴人类 HIS 的哪些能力。
4. 医院使用毛伙伴 HIS 时，如何证明数据不会被平台或竞争对手随意查看。
5. 医院病历如何回流到用户 App，并在用户后续去其他医院时形成可用病史。

## 3. 人类 HIS 系统的现实形态

## 3.1 HIS、EMR、EHR 的区别

| 系统 | 中文含义 | 核心职责 |
|---|---|---|
| HIS | 医院信息系统 | 挂号、收费、药房、医嘱、住院、检查检验申请、结算等医院运营流程 |
| EMR | 电子病历系统 | 医生病历、诊断、病程记录、手术记录、出院小结等医疗文书 |
| EHR | 电子健康档案 | 跨机构、跨时间的个人健康档案，通常由区域平台、医联体或公共卫生平台承载 |
| LIS | 检验系统 | 血常规、生化、PCR 等检验申请、结果和报告 |
| PACS/RIS | 影像系统 | X 光、B 超、CT、MRI 等影像检查、报告和影像归档 |
| 药房系统 | 药品管理系统 | 处方审核、发药、库存、批号、用药执行和追溯 |

人类医院的 HIS 通常是院内业务主系统。跨院共享不是 HIS 自身天然完成，而是通过区域医疗平台、医联体平台、医保平台、转诊平台、电子健康档案平台等外部协作层完成。

## 3.2 人类医院是否内部联网

人类医院内部通常会联网，主要是院内系统互通：

```text
挂号/预约
  -> 门诊接诊
  -> 医生开医嘱、处方、检查、检验
  -> 收费/医保结算
  -> 药房发药
  -> LIS/PACS 返回报告
  -> EMR 归档病历
  -> 住院/手术/出院小结
```

院内联网的核心目标是让同一家医院内部的科室、医生、药房、收费、检验、影像和住院部门协同。

跨医院共享通常依赖独立的平台和规则：

| 跨院场景 | 常见承载方式 | 共享特点 |
|---|---|---|
| 转诊 | 医联体平台、转诊单、区域医疗平台 | 共享转诊原因、诊断摘要、检查结果、用药摘要 |
| 复诊 | 患者带资料、互联网医院、区域档案 | 医生查看授权资料或患者提供的报告 |
| 检查检验互认 | 区域检验检查互认平台 | 共享报告结论和原始检查信息 |
| 医保/理赔 | 医保平台、商保直付/理赔平台 | 共享收费、诊断、处方、发票、病历摘要 |
| 公共卫生 | 疾控、公共卫生平台 | 共享特定疾病和风险事件 |

## 3.3 人类医院是否共享用药信息

人类医院会记录用药信息，常见记录包括：

| 用药记录 | 内容 |
|---|---|
| 门诊处方 | 药品名称、剂量、频次、用法、数量、开方医生、开方时间 |
| 住院医嘱 | 长期医嘱、临时医嘱、执行时间、执行人、停嘱时间 |
| 发药记录 | 药房发药、退药、批号、数量 |
| 出院带药 | 出院后继续使用的药品、疗程和注意事项 |
| 过敏/不良反应 | 过敏药物、反应类型、严重程度、记录来源 |

跨院共享时，用药信息通常以摘要方式共享，重点服务医疗安全：

| 信息 | 跨院共享价值 | 是否应共享 |
|---|---|---|
| 当前正在使用的药物 | 避免重复用药、相互作用和禁忌 | 应共享 |
| 近期处方和疗程 | 帮助新医生判断病程和治疗连续性 | 应共享 |
| 过敏和不良反应 | 直接影响生命安全 | 应优先共享 |
| 出院带药 | 支持复诊和延续治疗 | 应共享 |
| 医生完整治疗思路 | 涉及医疗机构内部专业判断 | 按权限和场景控制 |
| 医院内部备注 | 属于内部工作记录 | 默认不共享 |

这个模式对宠物 HIS 有直接参考价值：用药摘要属于医疗安全数据，完整治疗策略属于医院专业资产。

## 4. 毛伙伴宠物 HIS 的定位

毛伙伴 HIS 的目标不是简单替代宠物医院收银系统，而是建立宠物医疗协作基础设施。

## 4.1 与宠物店收银系统的区别

| 维度 | 宠物店收银系统 | 宠物 HIS |
|---|---|---|
| 核心对象 | 商品、服务、订单、会员 | 宠物、主人、就诊、病历、医嘱、处方 |
| 核心流程 | 下单、收银、库存、会员营销 | 接诊、检查、诊断、治疗、处方、复诊 |
| 数据价值 | 经营消费记录 | 医疗事实、健康档案、风险和理赔依据 |
| 关键约束 | 价格、库存、收银效率 | 医疗安全、病历完整性、权限和审计 |
| 平台延展 | 电商、会员、营销 | App 健康档案、转诊、保险、慢病管理 |

## 4.2 毛伙伴 HIS 应覆盖的核心流程

```text
宠物建档
  -> 预约/到院
  -> 分诊/接诊
  -> 主诉和体征记录
  -> 检查/检验/影像
  -> 诊断
  -> 医嘱/处方/治疗
  -> 收费
  -> 发药/耗材/库存扣减
  -> 病历归档
  -> 复诊提醒
  -> 健康档案发布到 App
  -> 转诊/保险/慢病协作
```

## 4.3 毛伙伴 HIS 的产品原则

| 原则 | 含义 |
|---|---|
| 宠物是医疗主体 | 所有就诊、用药、报告和保险材料归属到宠物档案 |
| 医院拥有原始病历 | 完整 HIS 数据属于医院租户，平台按合同和权限提供服务 |
| App 承载发布版健康档案 | 用户端看到的是医院发布或规则生成后的健康档案，不是医院原始数据库 |
| 跨院共享走授权 | 新医院只能在宠物主授权后查看指定范围、指定期限的数据 |
| 用药摘要服务安全 | 当前和近期用药、过敏、不良反应应进入可共享病史 |
| 治疗方案保护医院资产 | 方案模板、内部备注、成本利润和客户运营数据不进入共享层 |

## 5. 双层病历模型

毛伙伴 HIS 必须采用双层病历模型：医院原始 HIS 记录和宠物健康档案发布版分开。

| 层级 | 数据归属 | 内容 | 默认可见对象 |
|---|---|---|---|
| 医院原始 HIS 记录 | 医院 | 完整病历、处方、医嘱、收费、库存、医生内部备注、治疗方案、经营数据 | 本院授权员工 |
| 宠物健康档案发布版 | 宠物主可携带，来源医院可追溯 | 诊断摘要、报告、用药摘要、疫苗、手术摘要、复诊建议 | 宠物主、被授权机构 |
| 转诊/急救数据包 | 宠物主授权 + 场景限定 | 近期病史、当前用药、过敏禁忌、关键报告、转诊原因 | 被授权医院 |
| 保险理赔材料包 | 宠物主授权 + 理赔用途限定 | 诊断、费用、处方、报告、发票、时间线证据 | 被授权保险方 |

这套模型解决两个冲突：

1. 宠物主需要连续健康档案。
2. 医院需要保护完整病历、治疗经验和经营数据。

## 5.1 原始 HIS 记录

原始 HIS 记录用于医院内部业务，包含完整诊疗和经营信息。

| 数据 | 说明 |
|---|---|
| 原始主诉和病程 | 医生记录的完整问诊和病程信息 |
| 诊断和鉴别诊断 | 医生内部判断和诊疗方向 |
| 医嘱和处方 | 检查、检验、治疗、用药、护理、手术等 |
| 检验影像申请与报告 | 院内或外送检查的完整记录 |
| 收费和库存 | 项目收费、药品耗材、批号、成本和库存 |
| 内部备注 | 员工协作、风险提示、客户沟通备注 |
| 方案模板 | 医院沉淀的治疗路径、套餐和 SOP |

## 5.2 健康档案发布版

健康档案发布版用于用户 App、转诊、复诊和保险协作。

| 数据 | 说明 |
|---|---|
| 就诊摘要 | 就诊时间、医院、医生、主诉摘要、诊断摘要 |
| 生命体征 | 体重、体温、心率、呼吸、精神状态等 |
| 疫苗/驱虫 | 疫苗名称、批号、接种时间、下次提醒 |
| 检验报告 | 报告结果、异常指标、报告附件 |
| 影像报告 | 影像结论、关键图片、报告附件 |
| 手术/住院摘要 | 手术名称、麻醉情况、住院时间、出院建议 |
| 用药摘要 | 药品、剂量、频次、途径、起止时间、用药目的 |
| 过敏/不良反应 | 过敏源、反应、严重程度、记录来源 |
| 复诊计划 | 复诊时间、注意事项、检查建议 |

## 6. 病史跨院共享边界

宠物去另一家医院就诊时，新医院需要看到的是可用于诊疗判断的病史，而不是上一家医院的完整经营和治疗资产。

## 6.1 跨院可共享病史

| 类型 | 是否共享 | 原因 |
|---|---|---|
| 宠物基础信息 | 共享 | 品种、年龄、性别、绝育、体重影响诊疗判断 |
| 疫苗和驱虫记录 | 共享 | 入院、传染病风险、免疫状态判断需要 |
| 过敏和不良反应 | 优先共享 | 直接影响用药安全 |
| 重大诊断 | 共享 | 猫瘟、猫传腹、肾病、心脏病等影响后续治疗 |
| 检验报告 | 共享 | 新医生需要参考历史指标趋势 |
| 影像报告 | 共享 | 避免重复检查，辅助判断病程 |
| 手术/住院摘要 | 共享 | 麻醉风险、术后状态和既往手术史重要 |
| 当前和近期用药 | 共享 | 避免重复用药、相互作用和禁忌 |
| 复诊建议 | 共享 | 支持治疗连续性 |

## 6.2 默认不跨院共享的数据

| 类型 | 原因 |
|---|---|
| 医生完整病程笔记 | 涉及医生完整思考和机构内部医疗文书 |
| 内部备注 | 属于医院内部协作和客户沟通记录 |
| 治疗方案模板 | 属于医院专业经验和商业资产 |
| 药品成本、利润、供应商 | 属于医院经营敏感数据 |
| 客户标签和营销记录 | 属于医院客户资产 |
| 价格策略和套餐配置 | 属于医院经营策略 |

## 6.3 病史授权流程

```text
用户带宠物到 B 医院
  -> B 医院发起查看历史病史请求
  -> 用户 App 收到授权确认
  -> 用户选择宠物、数据范围、有效期
  -> 平台生成只读授权令牌
  -> B 医院查看健康档案发布版和授权数据包
  -> 所有访问写入审计日志
  -> 授权到期或用户撤回后停止访问
```

## 6.4 外院病史在新医院的使用方式

B 医院看到 A 医院产生的历史记录后，应将其标记为“外部病史引用”。

| 处理方式 | 说明 |
|---|---|
| 只读引用 | 不允许 B 医院修改 A 医院原始记录 |
| 来源标识 | 显示来源医院、记录时间、发布版本 |
| 医生确认 | B 医院医生可将关键信息纳入本次就诊病历 |
| 审计留痕 | 记录 B 医院查看和引用了哪些外部记录 |

## 7. 用药信息同步策略

用药信息需要同步，但必须以医疗安全摘要的方式同步。

## 7.1 应同步的用药字段

| 字段 | 是否同步 | 说明 |
|---|---|---|
| 药品通用名 | 同步 | 避免重复用药和相互作用 |
| 商品名 | 同步 | 便于用户和医院识别实际药品 |
| 剂量 | 同步 | 宠物用药高度依赖体重和剂量 |
| 频次 | 同步 | 判断是否正在用药和疗程强度 |
| 给药途径 | 同步 | 口服、注射、外用、输液等影响判断 |
| 开始/结束时间 | 同步 | 判断当前用药状态 |
| 对应诊断或用药目的 | 同步 | 帮助新医生理解用药背景 |
| 开药医院和医生 | 同步 | 支持追溯 |
| 不良反应 | 优先同步 | 直接影响安全 |
| 停药原因 | 建议同步 | 判断疗效或不耐受 |

## 7.2 不应同步的用药相关信息

| 字段 | 原因 |
|---|---|
| 药品采购价 | 经营敏感 |
| 药品利润 | 经营敏感 |
| 供应商 | 经营敏感 |
| 医院内部用药方案模板 | 专业资产 |
| 医生内部用药推理全文 | 医疗文书和专业判断 |
| 套餐组合策略 | 商业资产 |

## 7.3 猫瘟、猫传腹等病种的处理

猫瘟、猫传腹、慢性肾病、糖尿病、心脏病等病种常涉及较长疗程和复杂用药。跨院共享时应遵循：

| 内容 | 处理方式 |
|---|---|
| 确诊信息 | 共享 |
| 关键检验指标 | 共享 |
| 当前和近期用药 | 共享摘要 |
| 疗程阶段 | 共享摘要 |
| 复诊和复查建议 | 共享 |
| 完整治疗方案模板 | 不共享 |
| 医生内部调整策略 | 按医院配置和转诊场景控制 |

这能保障后续医院接诊安全，也能减少医院担心治疗经验被竞争对手复制。

## 8. 用户 App 回流设计

HIS 数据回流 App 时，必须走“发布版健康档案”机制。

## 8.1 回流链路

```text
医院完成就诊
  -> HIS 生成原始医疗记录
  -> 系统生成健康档案候选摘要
  -> 医生确认或医院规则自动发布
  -> 用户 App 收到健康档案更新
  -> 用户可查看、下载、授权给其他机构
```

## 8.2 App 展示内容

| App 模块 | 内容 |
|---|---|
| 宠物健康时间线 | 就诊、疫苗、驱虫、检查、手术、复诊、用药事件 |
| 病史摘要 | 重大疾病、慢病、手术史、过敏、不良反应 |
| 报告中心 | 检验、影像、病理、外送报告 |
| 用药记录 | 当前用药、近期用药、历史用药摘要 |
| 复诊提醒 | 医院建议、平台提醒、用户自定义提醒 |
| 授权管理 | 授权医院、保险方、家庭成员查看指定数据 |

## 8.3 发布方式

| 方式 | 适用场景 |
|---|---|
| 医生手动发布 | 复杂病例、敏感记录、需要医生判断的内容 |
| 医院规则自动发布 | 疫苗、驱虫、常规体检、标准报告 |
| 延迟发布 | 医院需要内部审核或补充报告 |
| 不发布 | 内部备注、争议记录、经营数据、方案模板 |

## 9. 后端数据信任架构

医院负责人会关心一个核心问题：

> 平台怎么证明医院数据不会被平台内部人员或竞争医院看到？

回答不能停留在口头承诺，必须形成系统、合同和审计三层证明。

## 9.1 技术隔离

| 能力 | 设计要求 |
|---|---|
| 多租户隔离 | 所有核心表强制 `tenant_id`，服务层强制租户上下文 |
| 独立数据库选项 | 中大型医院或连锁可选择独立数据库 |
| 独立对象存储 | 影像、报告、附件按租户隔离存储 |
| 字段级加密 | 手机号、身份证明、病历敏感字段、内部备注等加密 |
| 租户密钥 | 标准版平台托管密钥，高级版支持医院独立密钥或 BYOK |
| 最小权限 | 平台服务账号、运营账号、运维账号权限分离 |
| 数据导出 | 医院可导出本院完整数据，支持迁移 |

## 9.2 权限控制

| 角色 | 默认权限 |
|---|---|
| 医生 | 查看和编辑本人/本院授权范围内病历 |
| 助理/护士 | 查看接诊任务、执行医嘱、录入基础信息 |
| 前台 | 预约、建档、收费、客户沟通，不查看完整病程 |
| 药房 | 查看处方和发药信息，不查看完整内部备注 |
| 院长/管理员 | 配置人员权限、查看经营和审计报表 |
| 平台运营 | 默认无医院明文业务数据权限 |
| 平台运维 | 默认无业务查询权限，故障工单授权后限时访问 |
| 其他医院 | 仅能查看宠物主授权的数据包 |
| 宠物主 | 查看健康档案发布版和授权管理 |

## 9.3 审计和追责

| 审计项 | 说明 |
|---|---|
| 登录审计 | 账号、设备、IP、时间、角色 |
| 查看审计 | 谁看了哪只宠物、哪份病历、哪份报告 |
| 编辑审计 | 修改前后内容、修改人、修改时间、原因 |
| 导出审计 | 导出范围、文件、申请人、审批人 |
| 授权审计 | 授权方、被授权方、数据范围、有效期 |
| 平台工单审计 | 工单号、医院授权、访问原因、访问窗口、实际访问内容 |
| 异常告警 | 批量查看、异常导出、跨角色访问、非工作时间高频访问 |

## 9.4 合同和产品承诺

| 承诺 | 内容 |
|---|---|
| 数据归属 | 医院原始 HIS 数据归医院控制 |
| 使用范围 | 平台仅为提供 HIS、App 回流、授权协作和运维安全使用数据 |
| 模型训练 | 使用医院数据训练模型必须单独授权 |
| 经营分析 | 行业报告或聚合分析必须脱敏、聚合，并按合同约定 |
| 数据迁移 | 医院可导出本院数据，解除合作后按约定删除或归档 |
| 安全事件 | 明确通知、响应、补救和赔付责任 |

## 9.5 面向医院的证明材料

销售和合作阶段应准备一套“数据信任包”：

| 材料 | 用途 |
|---|---|
| 安全白皮书 | 说明租户隔离、加密、权限、审计和运维访问机制 |
| 数据流图 | 说明原始 HIS、健康档案、转诊包、保险包的边界 |
| 权限矩阵 | 说明不同角色能看什么、不能看什么 |
| 审计演示 | 给医院负责人演示如何查看访问日志和导出记录 |
| 工单授权流程 | 说明平台排障时如何获得医院授权 |
| 数据导出协议 | 说明停用系统后的数据迁移能力 |
| 模型训练授权条款 | 说明平台不会默认拿医院数据训练模型 |

## 10. 部署和商业档位

不同规模医院对数据控制的要求不同，系统应提供分层部署方案。

| 档位 | 适合对象 | 数据隔离能力 | 成本 |
|---|---|---|---|
| 标准 SaaS | 单店、小型医院 | 逻辑租户隔离、平台托管密钥 | 低 |
| 独立租户 | 中大型医院、区域连锁 | 独立数据库、独立对象存储、独立密钥 | 中 |
| 私有化/本地网关 | 大型连锁、强合规客户 | 私有部署或本地数据网关、医院自管密钥 | 高 |

建议第一阶段以标准 SaaS 起步，但底层数据模型必须按可升级到独立租户的方式设计。

## 11. 分阶段落地

## 11.1 第一阶段：单院 HIS 闭环

目标是让一家医院完整跑通内部业务。

| 能力 | 范围 |
|---|---|
| 宠物和主人建档 | 宠物基础信息、主人联系方式、院内客户关系 |
| 预约和接诊 | 预约、到院、分诊、医生接诊 |
| 病历 | 主诉、体征、诊断、处置、复诊建议 |
| 处方和收费 | 药品、服务项目、收费、退款 |
| 药品库存 | 药品、批号、库存、发药 |
| 报告附件 | 检验、影像、外部报告上传 |
| 基础权限 | 医生、前台、药房、院长 |
| 审计 | 登录、查看、编辑、导出 |

## 11.2 第二阶段：App 健康档案回流

目标是让医院记录转成宠物主可携带的健康档案。

| 能力 | 范围 |
|---|---|
| 发布版健康档案 | 诊断摘要、报告、用药摘要、疫苗、复诊 |
| App 时间线 | 就诊、报告、疫苗、用药事件 |
| 用户授权管理 | 授权医院、家庭成员、保险方 |
| 下载和分享 | 报告下载、转诊二维码、授权链接 |

## 11.3 第三阶段：跨院转诊和复诊

目标是让宠物在不同医院之间形成可控病史流转。

| 能力 | 范围 |
|---|---|
| 转诊数据包 | 近期病史、关键报告、当前用药、过敏禁忌 |
| 外院病史引用 | 新医院只读查看，必要时引用到本次病历 |
| 授权有效期 | 单次、7天、30天、长期 |
| 访问审计 | 用户和来源医院可查看访问记录 |

## 11.4 第四阶段：保险理赔和慢病协作

目标是将医疗记录用于保险理赔、慢病管理和长期健康服务。

| 能力 | 范围 |
|---|---|
| 理赔材料包 | 诊断、处方、报告、发票、时间线 |
| 慢病档案 | 肾病、心脏病、糖尿病、猫传腹等长期跟踪 |
| 复诊计划 | 医院计划、用户提醒、平台提醒 |
| 风险评估 | 在授权和脱敏前提下做风险建模 |

## 13. 医院负责人问答口径

| 医院问题 | 回答口径 |
|---|---|
| 你们平台是不是能看到我院所有病历？ | 后端为系统运行会处理医院数据，但平台人员默认无明文业务访问权限。任何运维访问都需要授权、工单、时间窗口和审计。 |
| 其他医院会不会看到我们的治疗方案？ | 其他医院只能在宠物主授权后查看健康档案发布版或转诊数据包，看不到内部备注、方案模板、成本利润和客户运营数据。 |
| 用户会不会拿完整病历去竞争医院？ | App 展示的是医院发布版健康档案。医院可配置哪些内容自动发布、哪些内容医生确认后发布、哪些内容不发布。 |
| 用药情况为什么要共享？ | 用药摘要关系到重复用药、药物相互作用、剂量和过敏禁忌，是医疗安全信息。共享的是药品、剂量、频次、起止时间等摘要，不包含采购价、利润和方案模板。 |
| 平台会不会拿我院数据训练模型？ | 医院原始数据默认只用于提供产品服务。模型训练、行业分析和商业化数据使用需要单独授权和合同约定。 |
| 停用系统后数据怎么办？ | 医院可导出本院完整数据，解除合作后按合同约定迁移、删除或归档。 |

## 14. 风险和决策点

| 风险 | 影响 | 建议 |
|---|---|---|
| 医院担心数据泄露 | 阻碍 HIS 销售和合作 | 优先建设权限、审计、导出和安全白皮书 |
| 用户希望拿到完整病历 | 可能与医院利益冲突 | 用健康档案发布版承接用户权益 |
| 其他医院需要更多病史 | 可能影响转诊质量 | 提供可配置的转诊包和医生补充说明 |
| 用药共享引发医院抵触 | 医院担心方案泄露 | 只共享医疗安全摘要，不共享治疗方案模板 |
| 平台后期做 AI 分析引发担忧 | 破坏医院信任 | 早期明确模型训练授权边界 |
| 数据模型早期设计过薄 | 后期难以支持独立租户和授权审计 | 从第一阶段就纳入 `tenant_id`、权限、审计和发布版记录 |

## 15. 产品铁律

| 铁律 | 含义 |
|---|---|
| 原始病历归医院 | 完整 HIS 数据属于医院租户，平台按合同和权限提供服务 |
| 健康档案归宠物主可携带 | 用户 App 承载发布版记录，支持授权给新医院 |
| 跨院共享授权制 | 每次共享都有对象、范围、用途、有效期和审计 |
| 用药摘要优先安全 | 当前用药、近期用药、过敏和不良反应用于保护宠物安全 |
| 医院资产默认保护 | 内部备注、方案模板、成本利润、客户运营数据不进入共享层 |
| 平台访问可证明 | 医院能查、能管、能追责平台和员工访问行为 |

## 16. 当前推荐决策

毛伙伴 HIS 当前应按以下方向推进：

1. 第一阶段先做单院 HIS 闭环，建立宠物患者、就诊、病历、处方、收费、库存和审计的基本模型。
2. 同步设计健康档案发布版，避免后期从原始病历直接向 App 暴露数据。
3. 后端从第一天按多租户、授权、审计和可导出设计，保留独立数据库和独立密钥升级路径。
4. 用药记录进入 App 和跨院数据包，但仅以摘要方式出现。
5. 对医院销售时主打“医院数据主权 + 用户健康档案 + 可审计授权共享”，这是毛伙伴区别于普通宠物医院 SaaS 的关键能力。
