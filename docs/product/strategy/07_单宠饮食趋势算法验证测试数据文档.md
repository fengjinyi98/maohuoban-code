# 单宠饮食趋势算法验证测试数据文档

- 创建时间：2026-07-05
- 文档性质：算法验证测试文档
- 适用范围：本地开发数据库、单宠饮食趋势摘要、储物柜物品详情喂食时间线、后续库存克数估算验证
- 非目标：本文不是目标文档、实施计划、接口契约、医疗诊断规则，也不是 seed 数据规范。

---

## 1. 测试目的

本轮测试只验证单宠、健康期、夏季场景下的饮食趋势算法表现。

核心验证点：

| 验证点 | 说明 |
|---|---|
| 30 天健康样本 | 连续 30 天喂食记录可被算法读取并形成健康窗口 |
| 分品类趋势 | 主粮、湿粮/罐头、零食、营养品分别进入趋势统计 |
| 模糊份量 | `少一点`、`正常`、`多一点` 能形成稳定分布 |
| 储物柜引用 | 每条喂食事件引用真实 `food_inventory_items.id`，物品详情页能看到喂食时间线 |
| 食品快照 | 每条事件带 `food_snapshot`，后续编辑储物柜物品不影响历史喂食展示 |
| 删除过滤 | 已逻辑删除的喂食事件不进入算法样本 |

本轮不写异常记录、不写就医记录、不写预防保健记录，因此所有新插入喂食样本的 `health_context` 预期为 `healthy`。

| 分类 | 物品 | ID | 品牌 | 规格 | 包装克重 | 库存数量 |
|---|---|---|---|---:|---:|---:|
| 主粮 | 高爷家益生菌猫粮 | `c18ec020-91c5-4ab2-84df-fc0c90da8aac` | 高爷家 | `1.5kg` | 1500 | 2 |
| 湿粮/罐头 | 巅峰鸡肉主食罐 | `9a158667-1258-4313-8119-4a689ffabc67` | ZIWI | `185` | 空 | 12 |
| 零食 | 冻干鸡肉粒 | `dbc19fee-09b1-497a-859a-7656a08f4e3b` | ouen | `500g` | 500 | 1 |
| 营养品 | 犬猫通用益生菌 | `eb82b2a2-5d7f-457c-9e4d-247a2aec153c` | 柴柒 | `50` | 空 | 1 |

说明：

| 问题 | 当前处理 |
|---|---|
| 罐头和营养品规格没有解析成克重 | 本轮仍写入喂食事件，用于验证分品类趋势；克重估算后续再补规格解析或数据修正 |
| 物品当前是 `sealed` | 插入喂食数据后，应把被引用物品更新为 `in_use`，符合“喂食后进入喂食中”语义 |

实际排查结论：

| 问题 | 结论 |
|---|---|
| 罐头和营养品为什么没有结构化克重 | 用户表单确实填写了规格，但当前前端只解析带明确单位的 `kg` / `g` 文本；`185`、`50` 这类无单位规格只写入 `spec`，没有生成 `package_weight_grams` |
| 是否属于用户输入问题 | 不是。罐头、营养品在产品语义里通常天然对应克/支/罐，不能要求用户额外补单位来维持算法闭环 |
| 当前后端能力边界 | 后端目前只接收并保存前端提交的 `package_weight_grams`，没有根据 `category + spec + package_unit` 在服务端推导结构化克重 |
| 对算法影响 | 罐头和营养品仍可进入分品类趋势、喂食频率和 HIS 事实流；克数估算和库存校准暂时不能覆盖这两个物品 |
| 后续修正方向 | 后端应补齐规格结构化能力，统一由服务端根据食品品类、包装单位和规格文本生成 `package_weight_grams`，避免同一业务规则散在前端 |

### 3.4 主粮 30 天设计

主粮每天 2 条，共 60 条。夏季场景下整体稳定，略有食欲下降。

| 日期范围 | 设计 |
|---|---|
| 2026-06-05 到 2026-06-14 | 正常为主，建立基线初期稳定样本 |
| 2026-06-15 到 2026-06-23 | 穿插少一点，模拟夏季轻微下降 |
| 2026-06-24 到 2026-07-04 | 恢复到正常为主，少量多一点 |

每日主粮 score 预期：

| 日类型 | 组合 | daily_score |
|---|---|---:|
| 稳定正常日 | 正常 + 正常 | 2.00 |
| 夏季偏少日 | 少一点 + 正常 | 1.75 |
| 食欲较好日 | 正常 + 多一点 | 2.25 |
| 明显偏少但健康日 | 少一点 + 少一点 | 1.50 |

份量分数沿用算法讨论稿：

| amount_text | score |
|---|---:|
| 少一点 | 0.75 |
| 正常 | 1.00 |
| 多一点 | 1.25 |

### 3.5 湿粮/罐头设计

湿粮每周 4-5 次，共 20 条。

### 3.6 零食设计

零食用于验证“零食也进入长期饮食结构”，但首期不应把零食增减直接解释成疾病风险。

### 3.7 营养品设计

用途：

| 验证点 | 说明 |

## 4. 事件写入格式

每条数据写入 `pet_events`。

| 字段 | 值 |
|---|---|
| `id` | 新 UUID |
| `pet_id` | `18a15a21-0543-4d05-bdf4-5599e290a04b` |
| `event_kind` | `daily` |
| `event_subkind` | `feeding` |
| `title` | `已喂` |
| `summary` | `{食品名称} · {份量}` |
| `visibility` | `private` |
| `actor_user_id` | `175ad047-0ca4-4c58-901a-f6e7e6a7d438` |
| `superseded_by_event_id` | `NULL` |

`event_payload` 格式：

```json
{
  "food_item_id": "<food_inventory_items.id>",
  "food_role": "main_food",
  "amount_text": "正常",
  "food_snapshot": {
    "name": "高爷家益生菌猫粮",
    "brand": "高爷家",
    "category": "main_food",
    "spec": "1.5kg",
    "package_weight_grams": 1500,
    "package_count": 1,
    "package_unit": "袋",
    "cover_asset_id": null,
    "cover_url": null
  },
  "is_default_food": false,
  "note": null,
  "attachment_asset_ids": []
}
```

不同品类只替换 `food_item_id`、`food_role` 和 `food_snapshot`。

## 5. 插入后预期算法表现

### 5.1 饮食趋势摘要

插入后调用宠物饮食趋势摘要时，预期表现：

| 项 | 预期 |
|---|---|
| 状态 | 不再只是 `collecting_baseline` 的原始英文输出 |
| 样本窗口 | 30 天 |
| 健康样本 | 30 天均为 healthy |
| 分段条 | 至少展示主粮、湿粮/罐头、零食、营养品 |
| 主粮占比 | 最高 |
| 湿粮占比 | 第二 |

## 6. 不应出现的表现

| 表现 | 判断 |
|---|---|
| 已删除的 2 条旧喂食进入趋势 | 算法过滤错误 |
| 主粮、湿粮、零食、营养品混成一个总基线 | 算法边界错误 |
| 只有主粮进入趋势，罐头/零食/营养品不展示 | 数据分类或前端展示错误 |
| 低频营养品触发健康风险 | 风险规则过度解释 |
| 没有异常记录却标记 abnormal/medical | 健康上下文投影错误 |
| 物品详情没有喂食时间线 | `food_item_id` 引用或详情读模型错误 |
| 删除态旧事件在列表/详情可见 | `superseded_by_event_id IS NULL` 过滤缺失 |

## 9. 当前算法实际验证结果

本节记录 2026-07-05 基于本地数据库 `diet_trend_validation_20260705_v1` 的实际复算结果。

### 9.1 样本完整性

| 项 | 实际结果 | 判断 |
|---|---:|---|
| 有效 feeding 事件 | 97 | 与测试设计一致 |
| 覆盖自然日 | 30 | 满足 30 天窗口验证 |
| 主粮记录天数 | 30 | 足以形成个体主粮基线 |
| 湿粮/罐头记录天数 | 20 | 足以形成湿粮补充摄入参考 |
| 零食记录天数 | 12 | 适合做低频事实和结构占比，不形成强判断 |
| 营养品记录天数 | 5 | 仅适合作为低频健康事实 |
| 异常/就医样本 | 0 | 本轮只验证健康期趋势，不验证异常对照 |

### 9.2 分品类结构

按 `少一点 = 0.75`、`正常 = 1.00`、`多一点 = 1.25` 复算，30 天总分数结构如下：

| 品类 | 总 score | 占比 | 产品含义 |
|---|---:|---:|---|
| 主粮 | 57.50 | 63.2% | 主要饮食来源 |
| 湿粮/罐头 | 18.50 | 20.3% | 稳定补充摄入 |
| 零食 | 10.00 | 11.0% | 奖励/互动型摄入 |
| 营养品 | 5.00 | 5.5% | 低频健康补充事实 |

验证结论：

| 结论 | 说明 |
|---|---|
| 分品类建模成立 | 主粮、湿粮/罐头、零食、营养品没有被混成一个总基线 |
| 当前输出具备用户可理解价值 | 可以表达“近 30 天饮食结构”，不是单纯流水列表 |

### 9.7 已发现的数据结构化问题

| 问题 | 影响 | 优先级 |
|---|---|---|
| `spec = 185` 的罐头没有生成 `package_weight_grams = 185` | 湿粮/罐头可进趋势，但不能做克数估算 | 高 |
| `spec = 50` 的营养品没有生成 `package_weight_grams = 50` | 营养品可进事实流，但不能做剂量趋势 | 中 |
| 规格结构化逻辑主要在前端 | 规则容易分散，后端无法保证数据契约 | 高 |

建议后续把规格结构化收口到后端食品资产用例层：

```text
食品入库请求
-> 服务端根据 category + spec + package_unit 解析单件克重

-> 喂食事件 food_snapshot 继承结构化克重
-> 饮食趋势 / 物品详情 / HIS 摘要共用同一数据来源
```
