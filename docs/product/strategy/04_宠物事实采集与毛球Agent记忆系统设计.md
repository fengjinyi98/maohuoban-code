## 1. 核心结论

宠物记录系统的产品定位不是宠物日记，而是：

> **宠物事实采集系统 + 毛球 Agent 的结构化记忆底座。**

毛球的长期价值来自结构化事实。用户不会长期填写复杂表单，因此系统必须把用户每天随手点击、换粮、喂食、异常反馈、聊天描述、商家履约和医院记录都转化为可被毛球查询、推理和追踪的事实。

| 结论 | 说明 |
|---|---|
| 记录是 Agent 的传感器 | 每次快捷记录、食品库变更、症状反馈都应沉淀为结构化事实 |
| 食品库是一期核心模块 | 主粮、零食和补剂是毛球理解排便、呕吐、食欲和过敏的重要上下文 |
| 表单不是主要入口 | 高频动作必须支持默认值、快捷按钮、聊天抽取和系统追问 |
| 追问是闭环，不是主流程 | 毛球只在事实不足、事实冲突或风险升级时追问用户 |
| 徽章奖励事实质量 | 徽章、经验和商业优惠应奖励有效记录、连续观察和闭环反馈 |

## 2. 问题定义

## 2.1 当前矛盾

| 矛盾 | 表现 | 设计判断 |
|---|---|---|
| 毛球需要结构化数据 | 没有饮食、排便、用药、症状趋势时，只能泛化回答或追问 | 必须建设结构化事实底座 |
| 用户不愿意填复杂表单 | 每天填写喂水、喂食、排尿、排便、精神状态会快速损耗记录习惯 | 高频记录必须一键化 |
| 宠物不会表达 | 主人主要靠印象判断，印象容易遗漏和失真 | 系统需要持续采集和主动追踪 |
| 异常可能延迟演变 | 一次拉稀可能后续发展为肠炎、细小等风险 | 症状记录后必须形成追踪链 |
| 商业激励需要真实行为 | 品牌优惠和徽章体系若只奖励打开 App，数据价值不足 | 激励必须绑定有效结构化事实 |

## 2.2 产品目标

| 目标 | 验收含义 |
|---|---|
| 降低结构化输入负担 | 用户在首页完成一次喂食、排便或异常记录时，主路径不超过 1 到 2 次点击 |
| 建立宠物事实时间线 | 日常、健康、食品、症状、用药、医院、商家事件都归入统一宠物事实账本 |
| 让毛球具备上下文工具能力 | 毛球能读取当前饮食、近期换粮、近期异常、健康提醒和症状追踪链 |
| 形成主动追踪闭环 | 拉稀、呕吐、换粮、用药、疫苗驱虫等事件可触发后续提醒和反馈写入 |
| 支撑徽章和商业任务 | 有效记录、连续观察、换粮反馈、食品档案可进入徽章与品牌优惠体系 |

## 3. 产品边界

## 3.1 本阶段必须纳入

| 模块 | 一期范围 | 目的 |
|---|---|---|
| 宠物事件账本 | 统一承载日常、健康、食品、症状、提醒反馈等事件 | 提供追加型事实底座 |
| 食品库 | 主粮、湿粮、零食、补剂；支持当前、尝试中、已停用状态 | 为饮食推理提供长期上下文 |
| 快捷记录 | 已喂、便便、精神食欲、异常症状 | 让用户随手生成结构化事实 |
| 症状追踪 | 拉稀、呕吐、不吃、精神差等异常后的次日追问 | 构成风险趋势和恢复趋势 |
| 毛球事实工具 | 查询当前饮食、近期饮食变化、近期症状、健康时间线、风险标记 | 支撑更精准回答 |
| 徽章接入点 | 连续观察、食品档案、换粮观察、异常追踪等信号 | 激励用户完成有效记录 |

## 3.2 本阶段暂不纳入

| 暂不做 | 原因 |
|---|---|
| 完整营养成分库 | 数据采集和商品标准化成本高，一期只需知道吃什么和何时变化 |
| 每日全量护理表单 | 会显著增加用户心智负担，违背低摩擦采集目标 |
| 品牌优惠券发放系统 | 先保留徽章和任务信号，商业结算与品牌投放后续独立设计 |
| 医疗诊断自动结论 | 毛球提供风险提示、追踪建议和就医提醒，诊断结论需医疗边界单独评审 |
| 药品库与护理用品库全量建设 | 一期食品库优先；用药先进入健康记录，药品库后续独立扩展 |

## 4. 总体架构

```text
用户低摩擦动作
  -> 快捷记录 / 食品库 / 聊天抽取 / 商家履约 / 医院回流
  -> pet_events 追加型事件账本
  -> 食品库、症状链、健康时间线、提醒任务
  -> Agent 事实投影视图
  -> 毛球工具查询与主动追踪
  -> 用户反馈
  -> 新事实写回事件账本
```

| 层 | 核心职责 | 示例 |
|---|---|---|
| 输入层 | 低摩擦采集事实 | 首页快捷按钮、食品库添加、聊天确认、通知反馈 |
| 事件层 | 保存原始事实 | `pet_events`、食品状态变更事件、症状事件 |
| 资产层 | 保存长期上下文 | 食品库、当前主粮、尝试中食品、过敏备注 |
| 投影层 | 为页面和 Agent 生成读模型 | 今日照护、近期换粮、症状追踪、健康提醒 |
| Agent 层 | 查询事实、解释风险、发起追踪 | 毛球回答、追问卡片、次日通知 |
| 激励层 | 奖励有效记录和闭环反馈 | 徽章、经验、品牌任务、优惠资格 |

## 5. 低摩擦采集策略

## 5.1 输入原则

| 原则 | 产品设计 |
|---|---|
| 默认值优先 | 喂食默认当前主粮，排便默认正常，精神默认平稳 |
| 点击即记录 | 首页高频按钮直接生成事件 |
| 修改才展开 | 只有切换食品、选择异常或补充说明时展开更多字段 |
| 资产复用 | 食品、药物、医院、医生、疫苗品牌等可被事件引用 |
| 聊天反向入库 | 用户对毛球说出的事实生成待确认事件 |
| 追踪由系统发起 | 症状、换粮、用药和健康提醒由毛球主动跟进 |

## 5.2 首页快捷事实按钮

| 按钮 | 默认结构化事件 | 展开条件 | 结构化价值 |
|---|---|---|---|
| 已喂 | 当前主粮喂食事件 | 用户切换食品、补充喂食量、备注 | 饮食时间线 |
| 便便正常 | 正常排便观察事件 | 软便、拉稀、便秘、带血、次数异常 | 肠胃趋势 |
| 精神不错 | 精神状态正常事件 | 嗜睡、焦躁、不爱动、异常兴奋 | 行为趋势 |
| 食欲正常 | 食欲正常事件 | 不吃、少吃、暴食、挑食 | 饮食风险 |
| 异常 | 症状选择入口 | 拉稀、呕吐、不吃、咳嗽、跛行等 | 症状链起点 |

## 5.3 食品库低摩擦录入

| 入口 | 用户动作 | 系统产物 |
|---|---|---|
| 搜索添加 | 搜品牌或商品名 | 标准食品候选条目 |
| 拍包装 | 拍主粮袋、罐头、零食袋 | OCR 与商品识别候选 |
| 扫条码 | 扫商品条码 | 命中商品库或生成待补条目 |
| 喂食时新增 | 点“不是这个主粮” | 顺手添加食品并生成喂食事件 |
| 聊天抽取 | 用户说“最近换了 XX 粮” | 待确认食品与换粮事件 |
| 订单导入 | 商城、品牌、商家订单进入 | 自动生成食品候选 |
| 品牌页收藏 | 点“我家在吃” | 加入食品库，可设为当前主粮 |

## 5.4 食品库一期字段

| 字段级别 | 字段 | 说明 |
|---|---|---|
| 必填 | 食品名称、类型、状态、适用宠物 | 保证毛球知道宠物当前吃什么 |
| 推荐 | 品牌、开始时间、包装照片、来源入口 | 支撑换粮、商品识别和追溯 |
| 可后补 | 口味、规格、适口性、用户备注 | 支撑后续推荐和用户回忆 |
| 后续增强 | 配料、营养成分、过敏风险、品牌标准库 ID | 支撑更深的营养分析和商业合作 |

## 5.5 食品状态

| 状态 | 含义 | Agent 使用方式 |
|---|---|---|
| 当前主粮 | 日常默认喂食食品 | 作为饮食基线 |
| 尝试中 | 近期新增或换粮过渡食品 | 拉稀、呕吐、食欲异常时重点关注 |
| 零食常用 | 非主粮但高频摄入 | 排便和过敏风险辅助上下文 |
| 已停用 | 曾经吃过，现在停止 | 支撑历史回溯 |
| 备用 | 家中有但不常吃 | 只作为弱上下文 |

## 6. 结构化事实模型

## 6.1 统一事件账本

现有后端已经具备 `pet_events` 与 `event_payload` 基线，后续不应为每种日常小项都创建顶级强表。推荐保持统一事件账本，按事件类型规范 payload，并用投影表或读模型承接查询效率。

| 字段 | 含义 |
|---|---|
| `id` | 事件 ID |
| `pet_id` | 宠物主体 |
| `event_kind` | `daily`、`health`、`diet`、`symptom`、`agent_followup`、`merchant`、`trade` 等 |
| `event_subkind` | `feeding`、`stool`、`diet_change`、`diarrhea`、`vaccine` 等 |
| `occurred_at` | 发生时间 |
| `source` | 用户快捷记录、用户表单、毛球聊天抽取、通知反馈、医院回流、商家履约 |
| `confidence` | 事实可信度 |
| `event_payload` | 类型化结构化数据 |
| `visibility` | 自己、共管成员、授权可见、公开 |

## 6.2 证据强度

| 事实来源 | 可信度建议 | 示例 |
|---|---:|---|
| 用户在喂食记录中明确选择食品 | 高 | 今天喂了某主粮 |
| 用户把某食品设为当前主粮 | 中高 | 近期换粮上下文 |
| 用户新增食品但未设为当前主粮 | 中低 | 家中可能有新粮 |
| 毛球从聊天抽取并经用户确认 | 高 | “最近换了渴望”确认写入 |
| 毛球从聊天抽取但未确认 | 低 | 仅作为候选事实，不进入强推理 |
| 商家或医院回流 | 高 | 医院就诊、处方、商家履约 |

## 6.3 关键事件类型

| 事件 | 子类型 | payload 核心字段 |
|---|---|---|
| 饮食事件 | `feeding` | `food_id`、`food_role`、`amount_text`、`is_default_food` |
| 食品变更 | `diet_change` | `from_food_id`、`to_food_id`、`transition_state`、`started_at` |
| 排便观察 | `stool_observation` | `stool_state`、`frequency`、`blood_visible`、`note` |
| 食欲观察 | `appetite_observation` | `appetite_state`、`related_food_id` |
| 精神观察 | `mood_energy_observation` | `energy_state`、`behavior_tags` |
| 症状事件 | `symptom` | `symptom_type`、`severity`、`started_at`、`attachments` |
| 症状追踪 | `symptom_followup` | `parent_symptom_event_id`、`status`、`trend` |
| 健康事件 | `vaccine`、`deworming`、`visit`、`medication`、`weight` | 品牌、药品、医院、体重、提醒等 |
| Agent 写入 | `agent_confirmed_fact` | `extracted_from`、`confirmed_by_user`、`linked_event_ids` |

## 7. 毛球 Agent 工具边界

## 7.1 工具读模型

毛球不应直接扫描全部原始事件做自由推理。后端需要提供面向 Agent 的结构化读模型，保证字段稳定、可解释、可审计。

| 工具视图 | 作用 | 示例查询 |
|---|---|---|
| `pet_current_diet_context` | 当前饮食上下文 | 当前主粮、尝试中食品、常用零食、补剂 |
| `pet_recent_diet_changes` | 近期饮食变化 | 近 7/14/30 天换粮、食品状态变化、喂食偏离 |
| `pet_recent_observations` | 近期日常观察 | 排便、食欲、精神、饮水、呕吐 |
| `pet_health_timeline` | 健康时间线 | 疫苗、驱虫、就诊、体重、用药 |
| `pet_symptom_threads` | 症状追踪链 | 拉稀事件及后续是否好转 |
| `pet_risk_flags` | 风险标记 | 幼宠、老年、慢病、近期用药、连续异常 |

## 7.2 拉稀场景决策流

```text
用户说“今天拉稀了”
  -> 毛球查询当前饮食上下文
  -> 查询近 7/14 天饮食变化和喂食偏离
  -> 查询近期排便、食欲、精神、呕吐和用药
  -> 查询疫苗、驱虫、年龄和风险标记
  -> 生成基于事实的回答
  -> 事实不足或高风险时提出追问
  -> 写入症状事件并安排次日追踪
```

| 数据状态 | 毛球策略 |
|---|---|
| 近期有换粮或尝试中新食品 | 明确提示饮食变化可能相关，并建议观察和过渡 |
| 近期无饮食变化但驱虫过期 | 提醒驱虫上下文，建议结合便检或就医 |
| 同时有呕吐、精神差、不吃 | 风险升级，优先建议尽快就医 |
| 事实不足 | 展示追问卡片补齐关键上下文 |
| 用户确认症状 | 写入 `symptom` 事件，并创建追踪任务 |

## 7.3 写入边界

| 写入场景 | 规则 |
|---|---|
| 用户明确点击快捷记录 | 直接写入事件 |
| 用户确认毛球抽取结果 | 写入确认事件和来源引用 |
| 用户聊天中模糊表达 | 生成候选事实，等待确认 |
| 毛球主动追踪得到反馈 | 写入 `symptom_followup` 或提醒完成事件 |
| 高风险医疗建议 | 写入风险提示记录，但不写入诊断结论 |

## 7.4 记忆隔离与越权诱导边界

毛球的记忆能力必须建立在后端授权后的结构化读模型上。用户诱导毛球读取其他用户、其他宠物或管理员数据时，毛球可以产生工具调用申请，但实际读取必须由后端 Agent Gateway 按登录态和授权关系决定。

| 边界 | 产品规则 |
|---|---|
| 宠物事实 | 以 `pet_id` 为根，只有当前用户拥有或被授权共同管理时可读 |
| 用户偏好 | 以 `user_id` 为根，毛球名字、语气、回复长度默认属于用户私有偏好 |
| 家庭偏好 | 以 `household_id` 为根，只对家庭成员可见 |
| 聊天摘要 | 用于节约 token，不作为强事实参与饮食、异常或医疗判断 |
| 候选事实 | 聊天抽取和模型推断先进入确认任务，用户确认后才写入事实账本 |
| 向量检索 | 私有记忆必须带 scope 和授权过滤，不能全库裸搜 |
| 缓存 | 上下文缓存 key 必须包含授权主体、scope、`pet_id` 和版本号 |
| 审计 | 毛球读取私有事实必须记录工具名、目标 scope、授权结果和引用事实 |

对应工程目标文档：`docs/engineering/agent-memory-security/00_毛球Agent记忆隔离与工具安全目标文档.md`。

## 7.5 安全审计与恶意尝试处置边界

毛球遇到越权诱导、宠物枚举、管理员模式诱导和批量探测时，产品层按安全事件处理。审计目标是形成可追溯证据链、识别持续恶意行为，并保护未授权数据不被泄露。

| 风险等级 | 产品判断 | 处理方式 |
|---|---|---|
| 低 | 偶发询问能否查看朋友宠物 | 拒绝请求，保持正常使用 |
| 中 | 多次尝试不同宠物名、芯片号、档案号 | 限速 Agent 私有工具，必要时要求重新验证 |
| 高 | 明确要求忽略权限、读取全库、管理员模式 | 暂时冻结 Agent 私有工具，生成安全告警 |
| 严重 | 批量枚举、脚本化请求、疑似撞库 | 暂停关键私有数据能力，进入人工审核 |
| 极高 | 成功越权返回或疑似数据泄露 | 启动安全事故流程，保留证据、修复漏洞、评估通知 |

产品约束：

| 约束 | 说明 |
|---|---|
| 工具拒绝优先 | 工具层成功拒绝的越权请求按风险累计处理 |
| 泄露单独升级 | 任何疑似未授权私有事实返回都进入安全事故流程 |
| 最小化留证 | 长期保存 hash、风险标签、目标摘要和引用 ID；完整原文只允许短期受控留存 |
| 处置可复核 | 限制、冻结、人工审核都必须能追溯到审计日志和风险事件 |
| 普通能力保留 | 风险限制优先作用于 Agent 私有工具和私有记忆检索，账号安全和申诉入口保持可用 |

## 7.6 非宠物问题与成本控制边界

毛球的产品身份是宠物照护 Agent，不承接通用聊天、百科问答、作文、代码、泛娱乐等非宠物问题。所有请求在加载宠物事实包和主 Agent 前先经过轻量意图闸门，避免非宠物问题消耗宠物上下文和主模型 token。

| intent | 产品范围 | 处理 |
|---|---|---|
| `pet_care` | 喂食、便便、精神、日常照护 | 正常进入毛球 |
| `pet_record_query` | 体重、疫苗驱虫、异常、喂食历史 | 正常进入毛球 |
| `pet_food` | 主粮、零食、储物柜、换粮 | 正常进入毛球 |
| `pet_health_risk` | 拉稀、呕吐、不吃、精神差 | 正常进入毛球并遵守医疗边界 |
| `emotional_pet_context` | 宠物去世、走失、照护焦虑 | 允许宠物相关陪伴 |
| `app_support` | App 怎么添加宠物、怎么记录体重 | 轻量回答，不加载宠物事实 |
| `off_topic` | 作文、代码、百科、非宠物闲聊 | 短拒答并拉回宠物照护 |
| `prompt_injection` | 忽略规则、改成通用助手、读取全库 | 拒绝并记录风险信号 |
| `cost_abuse` | 连续大量无关长问题、刷通用创作 | 限速、冷却或进入风险评分 |

默认拒答话术：

```text
我主要帮你处理宠物照护、记录和健康相关问题。这个问题超出了毛球的范围。
```

成本约束：

| 约束 | 说明 |
|---|---|
| 意图闸门前置 | 先判断问题范围，再决定是否加载宠物上下文 |
| off-topic 不读私有上下文 | 非宠物问题不读取 `pet_identity_context`、私有记忆和向量库 |
| App 帮助轻量化 | App 使用问题走规则或轻量模型，不消耗主 Agent |
| 连续无关请求限速 | 多次非宠物长问题进入 `cost_abuse` 风险信号 |
| 紧急宠物问题保留通道 | 限速策略不能阻断真实宠物健康风险请求 |

## 8. 主动追踪与通知闭环

## 8.1 追踪触发器

| 触发事件 | 默认追踪 | 反馈选项 | 写入结果 |
|---|---|---|---|
| 拉稀 | 次日追问 | 好了、还拉、更严重、已就医 | 症状趋势 |
| 呕吐 | 当天或次日追问 | 未再吐、又吐了、精神差、已就医 | 风险升级 |
| 换粮 | 3 天内观察 | 正常、软便、不吃、停止换粮 | 换粮耐受 |
| 用药 | 用药时间提醒 | 已服、漏服、不适、停药 | 用药依从性 |
| 疫苗/驱虫到期 | 到期提醒 | 已完成、延期、忽略 | 健康履约 |
| 连续异常 | 风险提醒 | 已预约、继续观察、已恢复 | 风险状态 |

## 8.2 追踪原则

| 原则 | 说明 |
|---|---|
| 高频症状必须闭环 | 拉稀、呕吐、不吃、精神差需要后续反馈 |
| 追踪问题要短 | 通知落地页优先给 3 到 4 个选项 |
| 反馈即事实 | 用户点“好了”也要写入事件，作为恢复证据 |
| 连续异常要升级 | 多天未恢复时提高提醒优先级 |
| 用户可关闭 | 用户可对单个症状链停止追踪 |

## 9. 徽章与商业激励

## 9.1 徽章接入原则

| 原则 | 说明 |
|---|---|
| 奖励有效事实 | 记录必须有结构化字段或完成追踪反馈 |
| 奖励连续观察 | 连续 3/7/30 天观察可形成习惯 |
| 奖励闭环 | 症状发生后的后续反馈价值高于单次记录 |
| 奖励食品档案 | 当前主粮、尝试中食品和补剂档案是 Agent 上下文资产 |

## 9.2 V1 可接入徽章

| 徽章 | 获得条件 | 数据来源 |
|---|---|---|
| 食品档案师 | 任一宠物完成当前主粮档案 | 食品库 |
| 换粮观察员 | 换粮后完成 3 次反馈 | 食品变更 + 追踪 |
| 肠胃观察员 | 完成 7 次排便记录 | 排便观察 |
| 异常追踪员 | 症状发生后完成至少 1 次后续反馈 | 症状链 |
| 七日照护 | 连续 7 天有有效宠物事实 | 事件账本 |
| 健康守护者 | 完成疫苗或驱虫记录并设置提醒 | 健康事件 |

## 9.3 品牌商业化预留

| 商业场景 | 记录任务 | 品牌价值 | 用户价值 |
|---|---|---|---|
| 新粮试吃 | 7 天换粮观察 | 真实适口性和排便反馈 | 优惠券、试吃装 |
| 零食反馈 | 3 次食用反馈 | 真实宠物偏好 | 优惠券 |
| 补剂观察 | 14 天连续记录 | 使用依从性和状态反馈 | 折扣或复购权益 |
| 品牌会员 | 当前主粮档案绑定 | 用户留存和复购线索 | 会员权益 |

品牌任务必须依赖用户授权和隐私策略，且只使用用户同意参与的任务数据。

## 15. 不变约束

| 约束 | 说明 |
|---|---|
| 宠物为主体 | 所有事实必须绑定宠物或可追溯到宠物 |
| 事件追加优先 | 关键事实以追加事件为主，修改需要保留审计或历史 |
| 医疗边界清晰 | 毛球提供健康提醒和风险提示，医疗诊断边界后续单独评审 |
| 用户授权优先 | 健康、食品和商业任务数据对外使用必须经过授权 |
| SwiftUI 无渲染副作用 | 快捷记录写入必须发生在用户事件或 Store 命令入口 |
| 后端分层不破坏 | 依赖方向保持 `http -> application -> domain` |

## 16. 风险与处理

| 风险 | 处理 |
|---|---|
| 用户仍觉得记录麻烦 | 首页优先一键事实按钮，复杂字段只在异常和编辑时出现 |
| 食品商品库不完整 | 允许用户自定义食品，标准商品库后续逐步补齐 |
| 数据过稀导致毛球仍需追问 | 引入证据强度和追问兜底，追问结果写回事实账本 |
| 徽章引发刷记录 | 同类事件限频，低质量重复记录不给高价值徽章进度 |
| 品牌任务影响信任 | 品牌任务必须显式标识、用户授权、数据范围可见 |
| 医疗建议风险 | 高风险场景优先提示就医，避免输出确定诊断 |
