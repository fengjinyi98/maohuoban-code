# 毛伙伴 01号文档：首页与底部 Tab 产品方向

- 文档版本：v0.1
- 更新时间：2026-06-13
- 适用阶段：首页 UI 设计稿生成、产品方向统一、后续信息架构拆解
- 关联文档：
  - `00_不做薄MVP的产品依据.md`

---

## 1. 核心结论

毛伙伴的新方向必须以宠物为主体。

人是记录者、管理者、决策者和交易参与者；宠物才是内容、关系、记录、医疗、交易与保险闭环的核心对象。

毛伙伴这个名字的核心含义是：

> **真正的毛孩子之间的伙伴关系。**

产品不是“宠物主题的人类社区”，而是：

> **让每只毛孩子都拥有自己的主页、时间线和伙伴关系。**

---

## 2. 底部 Tab 定档

底部 Tab 先定为 5 个：

| 顺序 | Tab | 核心职责 |
|---|---|---|
| 1 | 首页 | 当前宠物主体页 / 宠物工作台 |
| 2 | 宠物世界 | 基于宠物画像推荐的宠物事件流 |
| 3 | 同城 | 本地医院、猫舍、犬舍、宠物店、交易与服务 |
| 4 | 消息 | 私信、评论、交易沟通、商家咨询、系统通知 |
| 5 | 我的 | 主人账号、身份认证、订单、授权、设置 |

发布入口不作为独立 Tab。发布入口以全局 `+` 或首页快捷动作存在，语义是：

> **为当前宠物记录一次事件。**

---

## 3. 首页定位

首页不是传统 UGC 推荐流。

首页是当前身份下的宠物主体页：

| 用户身份 | 首页主体 |
|---|---|
| 普通养宠用户 | 一只或几只绑定宠物 |
| 情侣 / 家庭共同养宠 | 同一只宠物的多人管理空间 |
| 猫舍 / 犬舍 | 多只宠物、父母血缘、出生批次、健康状态、出售状态 |
| 宠物店 | 店内宠物、护理记录、寄养 / 洗护 / 商品服务关联 |

首页首要目标是让用户一打开 App 就知道：

> **这里的主角是我的毛孩子。**

---

## 4. 首页第一屏原则

首页第一屏不承接大量下滑查看更多功能。

完整内容流交给 `宠物世界`，本地履约和服务交给 `同城`，高频沟通交给 `消息`。

首页第一屏只承接与当前宠物强相关的内容：

1. 当前毛孩子是谁
2. 它今天怎么样
3. 现在需要记录或处理什么
4. 它和哪些毛孩子产生了关系
5. 最近发生过什么关键事件

---

## 5. 首页模块结构

| 顺序 | 模块 | 内容 | 目的 |
|---|---|---|---|
| 1 | 顶部身份栏 | `毛伙伴` 品牌、当前城市、身份状态、提醒入口 | 建立品牌与本地信任边界 |
| 2 | 当前毛孩子主卡 | 宠物大图、名字、年龄阶段、今日状态、一句话近况 | 建立宠物主体心智 |
| 3 | 毛孩子切换器 | 多宠物横滑切换；商家模式显示宠物组 / 批次 | 支持多宠物和经营方管理 |
| 4 | 今日照护 | 食欲、精神、排泄、体重、疫苗 / 驱虫 / 复诊提醒 | 承接日常记录和健康管理 |
| 5 | 快捷动作 | 记录日常、健康记录、预约医院、导入交易宠物 | 承接交易、医疗、记录闭环 |
| 6 | 今日伙伴 | 同窝、同城、同病种、同医院、同来源的一条高质量关系卡 | 制造毛孩子之间的惊喜连接 |
| 7 | 最近时间线 | 当前宠物最近 2-3 条事件 | 承接宠物一生的连续记录 |
| 8 | 商家看板适配 | 多宠状态、待回复、待补健康记录、预定 / 出售状态 | 支持认证商家的高频运营 |

---

## 6. “今日伙伴”机制

“今日伙伴”是首页差异化关键。

它不是普通推荐卡，而是宠物之间的关系提示。

| 类型 | 示例文案 | 触发依据 |
|---|---|---|
| 同窝伙伴 | 糯米可能遇到了同窝妹妹：奶盖 | 交易来源、出生批次、父母血缘 |
| 同城伙伴 | 附近有一只同龄布偶，也在适应新家 | 城市、年龄、品种、状态 |
| 同病种伙伴 | 有 3 只毛孩子正在记录猫瘟康复过程 | 健康事件、病程标签 |
| 同医院伙伴 | 也有毛孩子今天去了瑞派宠物医院复诊 | 医院实体、就诊事件 |
| 同来源伙伴 | 来自同一家猫舍的毛孩子更新了近况 | 商家实体、交易记录 |

它的目标是让用户感受到：

> **毛伙伴里的社交起点是宠物之间的关系，人只是帮它们表达、记录和联系。**

---

## 7. 宠物世界的边界

`宠物世界` 是完整 UGC 入口，但它推荐的是宠物事件、宠物关系和宠物经验。

推荐依据以宠物画像为核心：

| 推荐依据 | 示例 |
|---|---|
| 性格 | 胆小猫适应新家记录 |
| 年龄 | 幼猫到家第 7 天、换牙期、绝育期 |
| 位置 | 同城宠物、附近医院相关经验 |
| 病症 | 猫瘟康复、皮肤病、肠胃敏感 |
| 来源 | 同猫舍 / 同犬舍 / 同窝宠物 |
| 医院 | 同一家医院接诊过的宠物记录 |

传统 UGC 推荐是推荐“人可能感兴趣的内容”。

毛伙伴的推荐应该是：

> **这只宠物可能相关的宠物、事件和经验。**

---

## 8. 同城的边界

`同城` 是平台信任边界。

医院、猫舍、犬舍、宠物店、交易、线下履约都以同城为前提，原因是：

1. 降低交易欺诈和运输风险
2. 提升线下看宠、体检、复诊的可执行性
3. 便于平台验证商家、医院和服务质量
4. 保护用户、商家和平台三方权益
5. 为后续 HIS、保险、透明套餐提供试点基础

同城不做传统社区分组。

同城承接的是本地实体：

| 实体 | 作用 |
|---|---|
| 医院 | 预约、就医摘要、复诊、HIS 回流、透明套餐 |
| 猫舍 / 犬舍 | 交易、同窝、父母血缘、售后健康反馈 |
| 宠物店 | 洗护、寄养、商品服务、店内宠物记录 |
| 同城宠物 | 附近同阶段、同品种、同问题的宠物关系 |

---

## 9. 话题与社区原则

早期不做传统社区 / 小组。

原因是传统社区会带来大量创建、审核、冷启动和运营负担，也容易把产品主体重新拉回“人群运营”。

早期用以下三种结构承接内容聚合：

| 结构 | 作用 |
|---|---|
| `#话题` | 承接经验聚合、搜索、热点和长期内容沉淀 |
| 宠物关系标签 | 承接同窝、同城、同年龄、同病种、同医院推荐 |
| 实体页 | 承接医院、猫舍、犬舍、宠物店等本地可信节点 |

`#话题` 是辅助结构，不是主组织结构。

---

## 10. 发布入口原则

发布不是“发帖”，而是“记录一次宠物事件”。

发布流程的第一步应该围绕宠物，而不是围绕社区：

1. 选择宠物
2. 选择事件类型
3. 填写内容和附件
4. 选择可见范围
5. 系统自动补充关系标签和话题建议

事件类型包括：

| 类型 | 示例 |
|---|---|
| 日常 | 吃饭、玩耍、出门、情绪 |
| 成长 | 到家、换牙、生日、第一次洗澡 |
| 健康 | 疫苗、驱虫、体重、异常观察 |
| 医院 | 就诊、复诊、检查报告、处置记录 |
| 交易 | 看宠、体检、合同、交付 |
| 纪念 | 重要瞬间、长期回忆、告别 |

---

## 11. 普通用户首页状态

普通用户首页重点：

1. 当前宠物主视觉
2. 宠物切换
3. 今日照护
4. 快捷记录
5. 今日伙伴
6. 最近时间线

适合 UI 表达：

- 有温度，但不能幼稚
- 以宠物照片 / 形象为第一视觉
- 信息密度适中
- 管理功能收在清晰入口里
- 不做传统信息流首屏

---

## 12. 认证商家首页状态

认证猫舍、犬舍、宠物店首页重点：

1. 多宠物状态看板
2. 待补健康记录
3. 待回复咨询
4. 出售 / 预定 / 已售状态
5. 父母血缘与出生批次
6. 店内宠物最近事件

认证商家的首页不是“我的宠物”，而是：

> **机构宠物工作台。**

但底层仍然以宠物为主体，而不是以商家账号为主体。

---

## 13. UI 设计稿生成重点

用于生成首页 UI 设计稿时，重点表达以下内容：

| 重点 | 说明 |
|---|---|
| 品牌心智 | 毛伙伴是毛孩子之间成为伙伴的地方 |
| 第一主角 | 当前宠物必须是首屏最大视觉中心 |
| 关系惊喜 | 首页需要出现“今日伙伴”或类似关系卡 |
| 非传统社区 | 首屏不要做普通 UGC 推荐流 |
| 同城信任 | 城市、医院、商家、交易服务要有明确但克制的入口 |
| 多身份适配 | 普通用户与认证商家都能使用同一个 C 端 App |
| 事件记录 | 发布入口语义是记录宠物事件 |

设计稿可以优先探索 3 个方向：

1. **温暖陪伴型首页**：宠物大图、今日状态、伙伴卡更突出。
2. **轻管理型首页**：照护提醒、快捷动作、最近时间线更突出。
3. **多宠工作台型首页**：适合猫舍 / 犬舍 / 宠物店，多宠状态和待办更突出。

---

## 14. 当前定档

当前阶段先确认：

1. 底部 Tab 为 `首页 / 宠物世界 / 同城 / 消息 / 我的`。
2. 首页是宠物主体页，不是传统推荐流。
3. 宠物世界承接完整 UGC。
4. 同城承接医院、商家、交易和本地服务。
5. 消息必须常驻，支持普通用户和认证商家的高频沟通。
6. 早期不做传统社区，用 `#话题 + 宠物关系标签 + 实体页` 承接聚合。
7. 发布入口不作为独立 Tab，发布语义改为“记录一次宠物事件”。
